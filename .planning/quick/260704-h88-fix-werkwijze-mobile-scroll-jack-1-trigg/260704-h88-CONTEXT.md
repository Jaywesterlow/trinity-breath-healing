<decisions>
## Implementation Decisions (from user, directly stated — not a discussion round)

1. **Trigger point:** The horizontal-scroll phase must start only once the section/first card reaches the **vertical middle of the viewport** — not as soon as the section enters at the top/bottom edge like the current implementation.
2. **True scroll-lock during horizontal phase:** While horizontal card-scroll is active, vertical page scroll must be **fully disabled** — not just visually masked by a sticky/transform illusion (which is what the current, broken implementation does). This is a deliberate supersession of the prior quick task's locked decision ("no `preventDefault`, no scroll lock, native swipe fallback only") — the user has now explicitly asked for a real lock. Implement it properly this time, intercepting the input events needed (wheel/touchmove, and likely keyboard scroll keys — Space/PageDown/Arrow — while locked) so the page genuinely cannot scroll past the pinned section until the horizontal phase completes.
3. **Re-enable on completion:** Once horizontal scroll reaches the last card, vertical page scroll must resume normally, continuing past the section.
4. **Research first:** User explicitly asked to research established patterns for this before implementing — this is a well-known pattern (seen on many marketing sites: Apple product pages, Stripe, agency portfolio sites) and the user wants it done right, not reinvented from scratch. Look for real-world reference implementations / write-ups of the "scroll-jack" / "pinned horizontal scroll" pattern, scroll-lock techniques (wheel delta accumulation, touch delta accumulation, `overscroll-behavior`, `touch-action`), and how production sites handle the accessibility/reduced-motion escape hatches for this pattern.

### Non-negotiable carryovers from the original locked decisions (260704-fj7 CONTEXT.md) — still apply
- `prefers-reduced-motion: reduce` → scroll-jack fully disabled, falls back to plain vertical scroll + native horizontal swipe/snap on the card track (unchanged from before).
- Desktop (≥1024px) completely unaffected.
- All 3 cards remain in server-rendered initial HTML, unconditionally, in document order (SSG/AEO requirement).
- No keyboard focus trapping — Tab must still move focus through card CTAs normally. (Note: this is about **focus movement**, distinct from decision #2 above which is about scroll input while the section is actively locked — research should clarify how production implementations keep these separate: e.g. locking wheel/touch/scroll-key input during the pinned phase without disabling Tab-driven focus movement or `scrollIntoView` behavior.)

### Claude's Discretion
- Exact mechanism for the scroll-lock (body `overflow: hidden` toggle vs `overscroll-behavior` vs wheel-event `preventDefault` with delta accumulation vs Intersection Observer-driven state machine) — this is exactly what the research step should resolve.
- Whether "vertical middle of the viewport" is measured against the section top, the first card's center, or the pin wrapper's center — pick whichever produces the most natural-feeling trigger point once implemented; default to section/pin-wrapper center if no stronger signal emerges from research.
- How to handle a fast/flung scroll gesture that would otherwise skip past the trigger point entirely (e.g. a hard swipe on mobile) — research should surface how others handle this (common answer: intercept at the IntersectionObserver threshold and snap-engage, rather than relying purely on continuous position sampling).
