## Broken

### 1. The site has no working path to book, and its one visible CTA is a dead end
Every page's nav (and mobile menu) carries a single primary call-to-action, **"Maak een
afspraak"** (`src/lib/components/global/Nav.svelte:130`), which links to `/contact`. `/contact`
is a `StubLayout` stub (`src/routes/contact/+page.svelte`) whose entire content is one
paragraph and "Deze pagina komt binnenkort beschikbaar" ("this page will be available soon").
The landing page's own section list (`src/routes/+page.svelte:15-19`) is `Hero, Werkwijze,
OverMij, Behandelingen, Faq` — there is no Contact section mounted anywhere on `/`. So right
now there is no page on the entire site where a visitor can actually book the 30-minute Google
Meet, submit a contact form, or reach a booking widget — the one button whose entire job is to
start that flow sends them to a "coming soon" placeholder. This directly defeats the project's
stated core conversion goal. (`KNOWN-ISSUES.md` tracks the Contact section as deferred on a
separate branch; that branch is not merged here.)

### 2. Structured data emits literal "TODO_PHONE" / "TODO_PRACTITIONER_NAME" on every page
`src/lib/constants/brand.ts:21,27` still holds `practitionerFullName: 'TODO_PRACTITIONER_NAME'`
and `phone: 'TODO_PHONE'`. `src/lib/schema/shared.ts:51` (`professionalServiceNode.telephone`)
and `:59` (`personNode.name`) pass these straight through, unguarded, into the JSON-LD that
ships on **every single route** (these are `SHARED_NODES` in `buildGraph.ts`). Confirmed on the
live page:
```
"telephone":"TODO_PHONE"
"@type":"Person", ..., "name":"TODO_PRACTITIONER_NAME"
```
This is machine-readable garbage handed to Google Rich Results / AI Overviews / any AEO
consumer, on a health-and-wellness site whose stated core value is E-E-A-T trust signals. Worth
noting the codebase *does* have a guard pattern for exactly this — `getSameAs()` in
`shared.ts:19` checks `!BRAND.socials.instagram.startsWith('TODO')` before emitting it — it just
wasn't applied to `telephone` or `personNode.name`. `scripts/grep-placeholders.sh` does flag
these two lines at the source level, but only as non-blocking informational output; nothing
gates the *rendered* HTML/JSON-LD against a literal `TODO_` string reaching production.

### 3. Footer and Hero hardcode contact/social info that contradicts the declared source of truth
`brand.ts`'s own header comment says: "NAP SOURCE OF TRUTH (LGL-09) ... NEVER hand-edit
downstream copies — always update here first." Despite that, `Footer.svelte:62` hardcodes
`href="tel:+31612345678"` and `Footer.svelte:80,88,96` / `Hero.svelte:57,67,77` hardcode
`https://x.com/trinitybnh`, `https://facebook.com/trinitybnh`, `https://instagram.com/trinitybnh`
— none of it read from `BRAND`. This directly contradicts what `brand.ts` says about the same
facts: `socials.facebook: null // null until practitioner confirms presence`,
`socials.x: null // not active on X`, `socials.instagram: 'TODO_INSTAGRAM_HANDLE'`. So the
JSON-LD correctly omits Instagram/Facebook (because the guard checks for `TODO`/`null`), while
the visible page confidently links to live-looking social profiles and phone number that were
apparently never confirmed. That's an inconsistent NAP presented on the same page — a human
visitor and a crawler reading structured data get two different, contradictory stories about
how to reach the practice, and one of the phone numbers is a placeholder-shaped sequential
number that is very unlikely to be real. This is a trust and local-SEO problem independent of
the code-hygiene problem.

### 4. Site-wide WCAG 2.2 AA color-contrast failures (128 occurrences, all 15 routes)
`pa11y-ci` (WCAG2AA/HTML_CodeSniffer) reported **128 errors, 0 passes recorded, across all 15
routes**, every one of them `WCAG2AA.Principle1.Guideline1_4.1_4_3.G18.Fail` (1.4.3 contrast,
Level AA). Lighthouse's independent axe-core accessibility audit on `/` corroborates this
(`color-contrast` audit scores 0). Eight distinct underlying defects, most appearing on every
route because they live in global components:
- **Nav links** (Home/Werkwijze/Over mij/Behandelingen/Contact) — 3.22:1, needs 4.5:1.
  `color: var(--brand-muted)` — `src/lib/components/global/Nav.svelte:283`. Token
  `--brand-muted: #7a8c6e` (`src/app.css:21`).
- **The "Maak een afspraak" CTA button itself** — 2.73:1, the worst ratio found, on the site's
  one conversion button, present on every page. `background: var(--brand-border); color:
  var(--color-bg-sand)` — `src/lib/components/ui/interactions/ButtonLink.svelte:58-59`. Token
  `--brand-border: #b68a6b` (`src/app.css:23`).
- **Header logo subtext** ("Breath & Healing") — 4.43:1 — `.logo__sub { color: #7a6f4f }`,
  `src/lib/components/global/NavLogo.svelte:84`.
- **Footer logo subtext** (inverted variant) — 3.8:1 — `.logo--inverted .logo__sub { color:
  #afa483 }`, `NavLogo.svelte:96`.
- On the landing page only: hero body copy, treatment card descriptions/labels, the Werkwijze
  card body, the Over mij body/feature copy, and every section "eyebrow" label (Werkwijze,
  Over mij, Diensten, FAQ) all fail at 3.18–3.22:1 — all using the same `--brand-muted` /
  `--brand-border`-derived colors.

This is not a handful of edge cases — it's the two tokens the design system uses for all
secondary text and all button chrome, both under the AA bar, wired into components used on
every page. Given CLAUDE.md states this project targets WCAG 2.2 AA as non-negotiable, this is
the single biggest accessibility finding.

### 5. WCAG 2.2 SC 2.5.8 (Target Size) failure on the Behandelingen carousel dots
Lighthouse/axe flags `target-size` (score 0) on `/`: the carousel pagination dots
(`.treatments__dot-visual`, `src/lib/components/global/Behandelingen.svelte:361-372`) render at
**6.4×6.4 CSS px** inside an 11.2×11.2px hit area (`.treatments__dot`, lines 354-359) — WCAG
2.2's new SC 2.5.8 requires ≥24×24px (or sufficient spacing/an exception, neither of which
applies here). Axe reports both insufficient size and insufficient spacing to the neighboring
dot. Pa11y's htmlcs runner does not check this SC (it predates htmlcs's WCAG2AA ruleset), so
this would have gone unreported without also running Lighthouse/axe.

### 6. `robots.txt` points crawlers at the wrong sitemap domain
`static/robots.txt:40`: `Sitemap: https://trinity-breath-healing.vercel.app/sitemap.xml`. The
production domain (per `PUBLIC_SITE_URL`, and per every canonical/OG URL actually rendered) is
`https://trinitybnh.nl`. `scripts/check-robots.sh` validates bot-order and that *a* `Sitemap:`
line exists, but never checks it matches `SITE_URL`, so this drift isn't caught by CI. Any
crawler that honors `robots.txt`'s `Sitemap:` directive literally (rather than guessing) will
look for the sitemap on a stale Vercel preview alias instead of the live domain.

### 7. `og:image` / `twitter:image` reference a file that 404s
Every page emits `<meta property="og:image" content="https://trinitybnh.nl/og-default.jpg">`
and the matching `twitter:image`. `og-default.jpg` does not exist in `static/` —
`curl -I http://localhost:4184/og-default.jpg` returns `404`. Any social share (Instagram bio
link-out, WhatsApp, Facebook, X, LinkedIn) or AI-Overview thumbnail attempt will fail to render
an image. Already flagged as a TODO in `src/lib/seo/defaults.ts:43`, but it is actively broken
today, not just unfinished.

### 8. `/faq` is a linked, sitemapped, "coming soon" stub — while the real FAQ content lives only on `/`
`Footer.svelte` links to `/faq`. `/faq` is in `sitemap.xml` and allowed by `robots.txt`. But
`src/routes/faq/+page.svelte` is a `StubLayout` stub with no FAQ content and no `FAQPage`
JSON-LD — confirmed: `faq.html`'s JSON-LD graph has no `FAQPage` node, while `index.html`'s does
(nine well-formed Q&A pairs, e.g. "Wat is ademwerk en hoe werkt het?" with a full paragraph
answer — the FAQ content itself is good, it's just in the wrong place). A visitor who clicks
"FAQ" from the footer, or a crawler that indexes `/faq` expecting FAQ content because the URL
and sitemap say so, gets a placeholder. Already tracked in `.planning/notes/KNOWN-ISSUES.md`;
confirmed still true post-merge.

### 9. 14 of 15 indexable routes are placeholder shells, not stub-marked to crawlers
This is the roll-up of #8 and the general shape of the site: every route except `/` renders
`StubLayout` — one `<h1>`, one description paragraph, and "Deze pagina komt binnenkort
beschikbaar." All 14 are in `sitemap.xml` with `priority=0.5`, allowed by `robots.txt`, and
linked from the nav/footer on every page (confirmed: every stub-route href appears on all 15
pages in the crawl). Each does carry a correct, unique `<title>`/description/canonical/JSON-LD
`WebPage`+`BreadcrumbList` (see "Noise" below — the mechanics are fine), so this isn't a
technical defect in the SSG pipeline. But for a project whose stated core value is "SEO + AEO
discoverability of trustworthy, citeable content," shipping 14 near-empty "coming soon" pages
as fully crawlable, sitemapped URLs is a real liability: it's exactly the kind of thin content
that risks depressing the whole domain's perceived quality, and gives search engines/AI
crawlers nothing to actually cite for `/werkwijze`, `/over-mij`, `/behandelingen`, all four
`/diensten/*` service pages, `/blog`, `/artikelen`. This is presumably intentional
phased-rollout scaffolding (`FND-08` comment in `StubLayout.svelte` says exactly that: "14
reserved stubs; Phase 2+ deepens content"), but as of this commit it is live in this state.

## Risky

### External Google Fonts CDN dependency, contradicting the project's self-hosted-fonts policy
Two separate components independently inject a Google Fonts `<link rel="stylesheet">` for
Cinzel/Montserrat, each already marked `TODO: self-host … (FND-06)`:
- `src/routes/+layout.svelte:51-57` — `Montserrat:wght@300;400`
- `src/lib/components/global/NavLogo.svelte:5-12` — `Montserrat:wght@300` (a different, narrower
  weight set)

Because the two `<link>` hrefs differ, Svelte's `<svelte:head>` doesn't dedupe them — the app
issues **two separate external stylesheet requests** for overlapping subsets of the same font
family. In this sandboxed container (no egress to `fonts.googleapis.com`) both fail outright
(`net::ERR_CONNECTION_RESET`), producing two console errors on every single route load. CLAUDE.md
lists self-hosted fonts (`fontaine`, `font-display: swap`, preloaded local woff2) as the chosen
architecture; this is a real, acknowledged (TODO-tagged) departure from it, and independent of
whether the sandbox can reach Google — it's an extra DNS+TLS round trip and a third-party
render-blocking dependency in production, which cuts directly against the stated LCP/perf
budget. Two components maintaining separate, drifting copies of the same external dependency is
also its own small bug on top of the architectural one.

## Noise

- **`structured-data-testing-tool` reports "Schema.org schemas: 0" and the `Google` preset runs
  no tests.** This looks alarming but is a tool limitation, not a site defect: `sdtt` v4.5
  doesn't parse `@graph`-wrapped JSON-LD (this project's format, per `schema-dts` and
  `SCH-01`'s single-`@graph`-per-page design). Manually parsing the same JSON-LD confirms it's
  valid, well-formed JSON with 10 correctly-typed nodes per stub page (12 on the landing page,
  including `FAQPage`) — and `npm run audit:json-ld` (which does understand `@graph`) passes
  clean on all 15 files. `sdtt`'s Twitter/Facebook preset results (the meta-tag findings above)
  are still valid and are reported under Untidy.
- **Google Fonts console errors observed in this container are partly a sandbox artifact.** The
  underlying architectural issue (external font CDN, contradicting FND-06) is real and is
  reported under Risky, but the specific `net::ERR_CONNECTION_RESET` / occasional `404` seen
  here reflect this container's blocked egress to `fonts.googleapis.com`, not necessarily a
  production failure mode — in production the request would very likely succeed, just slower
  and less reliably than a self-hosted font.
- **Repeating Organization/ProfessionalService/Person/WebSite/Service nodes on every page is
  correct practice, not duplication.** This is the standard, recommended pattern for
  `LocalBusiness`/`ProfessionalService` schema.org markup — the same real-world entity should
  be described consistently everywhere it's referenced, via stable `@id`s
  (`buildGraph.ts`'s dedup-by-`@id` logic is exactly built for this). A naive "same schema on
  every page" flag would be a false positive; the one genuine wrinkle (legal pages carrying the
  full service catalog) is called out separately under Untidy.
- **Dead-CSS-variable guard: clean.** Ran the exact logic from
  `tests/integration/no-dead-css-vars.spec.ts` against all 15 routes (the spec itself only
  covers `/` and `/contact`) — zero dead `var(--x)` usages found anywhere (65 unique vars
  checked on `/`, 41 on each stub route). `bash scripts/check-tokens.sh` also passes. No
  finding here; noted so the check doesn't read as skipped.
- **Headings: clean on every route.** Exactly one `<h1>` per page (15/15), no skipped levels
  anywhere. Landing page sequence: `h1, h2, h3×3, h2, h3×2, h2×5`. Every stub page:
  `h1, h2, h2, h2`. `npm run audit:html` (which asserts this structurally) also passes.
- **JSON-LD script count: clean.** Exactly one `<script type="application/ld+json">` per page,
  everywhere — the "never two JSON-LD scripts" invariant in `buildGraph.ts`'s docblock holds.
- **Images: clean.** All images across all 15 routes report `naturalWidth > 0` and either carry
  meaningful `alt` or are correctly marked `alt="" aria-hidden="true"` as decorative — including
  the header/footer logo icon, which is decorative *correctly*: the enclosing `<a>` has an
  explicit `aria-label="TRINITY Breath & Healing — naar home"`, so the accessible name doesn't
  depend on the image or the adjacent visible text at all.
- **Titles and descriptions: no duplicates.** All 15 titles and all 15 descriptions are
  distinct text (checked exact string equality, not just length). `hreflang` (`nl` +
  `x-default`), canonical URLs, and `og:locale: nl_NL` are all present and correct on every
  route checked.
- **AI-crawler-visible initial HTML: clean.** `npm run audit:initial-html-ai` (spot-checked with
  `ClaudeBot` on `/` and `OAI-SearchBot` on `/faq`) confirms the prerendered HTML already has
  the title, one `<h1>`, and the full JSON-LD graph with zero client-side rendering — no
  SPA-blocks-crawlers risk.
- **`reveal.ts` (the new scroll-fade-in system) is well-built.** Explicitly bails under
  `prefers-reduced-motion: reduce` before touching any style; Svelte actions never run without
  JS, so the no-JS degrade is "stays at its natural visible state" by construction, not a
  separate code path that could drift. Also documents and works around a real cross-component
  bug it discovered (animating `transform` broke the FAQ disclosure's own `grid-template-rows`
  transition) rather than leaving it latent. No console errors attributable to any of the new
  polish-pass work (hero cascade, Werkwijze view-timeline, FAQ disclosure, scroll-reveal,
  re-timed draw-ons) on any route.
